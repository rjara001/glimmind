## 3. Decisions

- **Library:** `react-i18next` + `i18next` (industry default, lazy namespace
  loading, React 19 compatible). No other candidate is evaluated in this plan;
  reconsider only if install fails.
- **`es` is the source of truth first** (P1–P3 land a single neutral-ES locale);
  `en` is a translation pass over the finished key set (P5), never before.
- **Extraction granularity:** one namespace per feature area
  (`common`, `nav`, `auth`, `dashboard`, `game`, `editor`, `store`, `onboarding`,
  `settings`, `errors`) so PRs stay reviewable.
- **Out of scope:** `error.message` → friendly copy mapping beyond the toast
  layer (tracked as U-11, `P2/2026-10-16-error-message-crudo-en-cliente.md`;
  P3 here only routes toasts through the i18n layer so U-11 can land on top);
  localized legal pages, decks, pricing (I-6..I-8 — `BUSINESS_MODEL.md` owns
  pricing); `hreflang`/sitemap (I-9 — SEO phase).

### 3a. Refinement decisions (adopted 2026-10-25)

- **Type-safe keys via `CustomTypeOptions`, not a manual union.** The
  catalogues are the type source: `src/@types/i18next.d.ts` augments
  `react-i18next` with `defaultNS: 'common'` and `resources: { common: typeof
  esCommon, nav: typeof esNav, ... }` inferred from the `es` JSON imports.
  `t('nav.title')` is autocompleted and unknown keys fail `tsc`, so the
  planned `Record<string, string>` + `TranslationKey` union (old P2-2) is
  dropped. Verified: `tsconfig.json` has `strict: true` and
  `resolveJsonModule: true`; `include: ["src"]` covers `src/@types/`.
- **Resource format: `.json` files** (`src/i18n/es/common.json`, …), flat
  objects per namespace. JSON keeps the catalogues importable by external TMS
  tooling (Crowdin/Phrase/Locize) later and pairs with `resolveJsonModule`.
  If a catalogue ever needs logic, it stays a flat `as const` object literal —
  no functions, no nesting beyond one level of grouping.
- **Loading: static bundling for now.** All `es` + `en` namespaces ship in the
  initial bundle; at 2 locales and ~10 small JSON files the cost is negligible.
  Revisit `i18next-http-backend` or per-namespace `import(...)` only if the
  project grows past **5 locales** (market plan Phase 5) — then split without
  changing the key space.
- **No string concatenation, ever.** Counts/plurals go through i18next
  interpolation with the `count` option (`t('dashboard.item_count', { count })`
  backed by `_plural`/`_other` key variants), dates and numbers go through the
  `Intl` API (`Intl.DateTimeFormat`, `Intl.NumberFormat`) or i18next formatters.
  `t('a') + ' · ' + t('b')` and hardcoded `1 elemento` suffixes are rejected at
  review in P3-1/P3-2.

## 5. Risks

| Risk | Mitigation |
|---|---|
| Extraction touches 97 components → huge diff | namespace-by-namespace with a green gate after each (P3 rule) |
| Tests break en masse on string change | single `tests/helpers/i18n.ts` wrapper + assert via catalogue keys (§37) |
| Switcher adds a global state that fights the store | language lives in i18next only; no `gameStore` field |
| `en` ships half-translated | key-parity test in P5-2 blocks it |
| A namespace exists on disk but not in `CustomTypeOptions` → its keys type as `never`/fail `tsc` | rule: the PR that adds `src/i18n/es/<ns>.json` also adds the `typeof` entry to `src/@types/i18next.d.ts` (P2-2 pattern) |

## 6. Explicit non-goals

- No per-route SEO meta (Phase 3 of the market plan).
- No localized decks, legal pages, or pricing (I-6..I-8; pricing decision
  belongs to `docs/BUSINESS_MODEL.md` per AGENTS §44).
- No `hreflang`/sitemap (I-9, depends on I-1..I-4 + SEO phase).
- No `pt-BR`/`fr`/`de`/`ja` (market plan Phase 5), but P2's `supportedLngs` and
  P5's parity test make them additive.
